# 初回に終了画面が出た件の調査（2026年11月3日）

対象：11月2日夜、iPad の Safari で参加用のアドレスを初めて開いたとき「この部屋は終了したか、有効期限が切れました」と表示された。2回目以降は起きていない。「確認用：」の行は事故のあとに追加したため、事故時の理由は記録されていない。

## 1. 子ども側の状態の移り変わり（現状のコード）

```
ページ読み込み
 → signInAnonymously を待つ（この間は全セクション非表示＝真っ白。失敗すると白いまま）
 → runChild：show('waiting')
   → requestToJoin：get(requests/自分) → get(members/自分) → 無ければ set(requests/自分)
       いずれかが例外 → catch → 「確認用：」に理由を書き show('closed')   ← 終了判定①
   → onValue(members/自分)：役割あり → runActivity／無し → waiting
       役割を失った → requestToJoin をやり直し、失敗なら closed              ← 終了判定②
 → runActivity：onValue(counters)：null → closed（先生が削除）            ← 終了判定③
                                  読み取り拒否（期限切れ等）→ closed     ← 終了判定④
先生のアドレス（&teacher=1）を開いた場合：
 → runTeacher：onValue(rooms/部屋)：読み取り拒否 → closed（「確認用」は出ない） ← 終了判定⑤
```

### 認証の完了前に画面が進んでいないか
進んでいない。`signInAnonymously` を最上位の `await` で待ってから `runChild` に入る。Database SDK（11.10.0）の接続手順も読んだ：接続前にトークンを取得し、接続後に auth を送ってから、待たせていた `get`／`listen` を同じ接続で順に送る。認証前に読み込みが先に届く経路は見当たらなかった。

### データの読み込みが終わる前に「終了」と判定していないか
判定①は「読み込みが終わる前」ではなく「読み書きが失敗した」ときに出る。ただし **失敗の理由を区別していない**：Rules の拒否（部屋が無い・期限切れ・削除済み・先生自身の uid）も、通信の失敗も、すべて「終了」と表示する。これは設計上の弱点で、原因の候補のうち複数がここに落ちる。
判定③は counters が null のとき。承認（roles・members をまとめて書く）と同じ更新で読めるようになるため、承認直後に null が来る経路はない。

## 2. 原因の候補（確定していない）

| 候補 | 起きる条件 | 再現（エミュレータ） | 「確認用」の行 |
|---|---|---|---|
| A. 先生のアドレス（`…&teacher=1`）を iPad で開いた | 先生画面を出した直後、Mac のアドレスバーは `?room=…&teacher=1` になる。これを Handoff・AirDrop・コピーで iPad に渡すと、iPad は先生の画面を開こうとし、部屋の読み取りを Rules が拒否して終了画面になる | **再現した**（判定⑤、終了画面、確認用の行は空） | 出ない |
| B. 部屋 ID の写し間違い（24文字） | 手で打つ・一部が欠ける | **再現した**（判定①、`PERMISSION_DENIED／部屋 23文字`） | 出る |
| C. 先生と同じブラウザで参加用アドレスを開いた | uid が作成者と同じなので参加希望が拒否される | 未再現（iPad では起きない） | 出る |
| D. 初回の通信の失敗（接続の確立前・遅い回線） | `get` が例外になる | 未再現。SDK 11.10.0 では接続できるまで `get` を待たせる実装で、古い版の「Client is offline」は該当しない | 出る（Error …） |

- 2回目以降は起きていないこと、事故時に「確認用」の行がまだ無かったことから、**A か B の可能性が高い**。A は「2回目は画面に表示された参加用リンクを使った」なら説明がつく。
- どれも確定ではない。再発時は「確認用」の行の有無と内容で A（出ない）と B／C／D（出る）を切り分けられる。

## 3. 画面の状態を区別できるか（検討）

子どもは承認されるまで部屋のデータを読めない（Rules）。そのため **承認前**に分かるのは「参加希望が受け付けられた／拒否された／通信できない」だけで、拒否の理由（部屋が無い・期限切れ・削除済み）は区別できない。**承認後**は meta（expiresAt）と counters を読めるので、期限切れと先生による終了を区別できる。

| 状態 | 今の表示 | 提案する表示 | 判定 |
|---|---|---|---|
| 読み込み中（認証・最初の通信） | 真っ白 | 「つないでいます」 | 認証完了と最初の応答まで |
| 承認待ち | 「先生が参加を承認するまで待ってください」 | 同じ | 参加希望の書き込み成功 |
| 参加できない（取得前の拒否） | 「終了したか期限切れ」 | 「この部屋には参加できません。アドレスを確かめてください」 | 参加希望が PERMISSION_DENIED |
| つながらない | 「終了したか期限切れ」 | 「つながっていません。そのままお待ちください」＋自動で再試行 | 通信エラー、`.info/connected` が false |
| 先生による終了 | 「終了したか期限切れ」 | 「先生が活動を終えました」 | 承認後、counters が null |
| 期限切れ | 「終了したか期限切れ」 | 「時間切れです」 | 承認後、サーバー時刻 ≥ expiresAt |
| 先生のアドレスを子ども端末で開いた | 「終了したか期限切れ」 | 「この端末では先生の画面を開けません」＋この部屋の参加用リンク | 先生画面の読み取り拒否 |

## 4. 修正案（承認後に実装）

1. **終了判定の理由を分ける**：`requestToJoin` の catch で `e.code === 'PERMISSION_DENIED'` だけを「参加できない」にし、それ以外（通信）は「つながっていません」のまま自動で再試行する（終了とは表示しない）。
2. **読み込み中の画面**を追加し、認証と最初の通信が終わるまで表示する。`signInAnonymously` の失敗も同じ画面で再試行する（今は真っ白）。
3. **承認後の区別**：counters が null → 「先生が活動を終えました」。meta の expiresAt を読み、サーバー時刻を過ぎたら「時間切れです」（読み取り拒否もこちらに倒す）。
4. **先生のアドレスを他の端末で開いた場合**：先生画面の読み取り拒否を「この端末では先生の画面を開けません」にし、`&teacher=1` を除いた参加用リンクを示す。先生側では、画面に出す参加用リンクを今より目立たせ、アドレスバーの URL を渡さないよう注意書きを付ける（A の再発防止）。
5. **「確認用：」の行**：1〜4 で理由が画面の状態として分かるようになるため、Q4 どおり外す。
6. 純粋ロジック（エラーの分類、状態→画面の対応）を `logic.js` に置き、クライアントテストを追加する。Rules は変更しない。

見込み：1.5〜2 時間（テスト・エミュレータ確認・Hosting 公開を含む）。
