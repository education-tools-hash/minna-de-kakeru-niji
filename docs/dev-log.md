### テストを先に書く → Rules を書く
1. Rules を全面拒否のまま、テスト36件（34件＋正常系の基準2件）を書いた。結果は **14件失敗・22件成功**。成功した22件は「拒否されること」を確認するテストなので、全面拒否でも通る。ログは `niji-shots/20261102-1812_rules-test_1-before-rules.log`、コミット `5300408`。
2. Rules の初版で実行すると、**2件失敗**（A8・A17）した。
   - A8 はテストの誤り：教員が作成者 uid を「同じ値で」上書きする操作は、値が変わらないため成功してよい。テストを「別の uid に書き換える」形に直した。
   - A17 は **Rules の穴**：初版では教員に部屋全体への書き込みを許可していた（`.validate` でカウンタの条件は守られる、という机上メモ §1-6 の考え方）。そのため教員が自分の参加希望を書けた。さらに調べると、**教員が子どものカウンタを＋1 できる**（増分の条件は満たすので `.validate` を通ってしまう）ことが分かった。これは代理参加にあたり、「対等参加」と「子どもの状態は本人だけが書く」の原則に反する。
   - 対応：教員の書き込み権限を部屋全体から外し、`roles/$role`・`members/$uid`・`requests/$uid`（削除のみ）の必要なパスだけに絞った。部屋単位で教員に許すのは「作成」と「削除」だけにした。回帰テストとして **A19（教員は子どものカウンタを書けない）** を追加した。同日夜に Nishio が追加を承認した。
3. 修正後、**37件すべて通過**。ログは `niji-shots/20261102-1817_rules-test_2-all-passed.log`。
4. テストが本当に効いているかを確かめた。
   - 修正前の Rules に戻すと、A17・A19 が失敗する（穴は実在した）。
   - 増分条件のうち「旧値 ≤ 相手の値」をわざと外すと、B4 が失敗する（テストが改変を検出できる）。

### ④ 最小画面（エミュレータ上、ブラウザの3タブで確認）
- 先生の画面（部屋作成・参加希望の承認・役割の解除・終了削除）と子どもの画面（タップ／スワイプ／マウス＝指やボタンを離した時点で1回、Space／Enter＝押しっぱなしの自動リピートは数えない）を作った。虹と共同変化の見た目は仮のもの。
- 確認できたこと（ブラウザの3タブ。実機ではない）：
  - 2人の参加希望が別々の匿名ユーザーとして届き、承認すると A・B に割り当てられた。
  - A が連打（クリック3回＋Space）しても待機は1件のまま。B 側には「ともだちの光が待っています」と表示された。Space でページはスクロールしなかった。
  - B の Enter で、両方の画面で虹が完成した（共同成立1）。
  - B の画面を再読み込みすると、虹は演出なしで静止表示された（C3）。その後、両者が1回ずつ参加すると、共同変化が両方の画面で1回だけ再生された。
  - 役割 A を解除すると A の画面は承認待ちに戻り、参加希望が出し直された。再承認で続きから再開できた（A18 の画面での流れ）。
  - 終了操作で3画面とも「終了」表示になった。
- 確認中に見つかった不具合：終了時、子どもの画面が「終了」ではなく「承認待ち」に戻っていた。役割が消えたことしか分からず、解除と終了を区別できていなかったため。役割を失ったら参加希望を出し直し、Rules に拒否されたら（＝部屋がない）終了と判断するよう修正した。
- 実機（iPad Safari・Blue2）での確認は**未実施**（E1〜E4）。
